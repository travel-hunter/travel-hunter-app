## Prototype Structure

프로토타입은 실제 API 없이 내부 상태만으로 화면을 전환한다. 사용자는 로그인 후 모바일 앱처럼 하단 탭을 통해 홈, 정책, 일정, 마이페이지를 오간다.

확인된 주요 화면은 다음과 같다.

| 화면 | 사용자 역할 |
| --- | --- |
| 로그인 | 앱 진입, 이메일/비밀번호 입력, 소셜 로그인 mock CTA |
| 홈 | 오늘 챙길 혜택과 추천 여행/일정의 첫 진입점 |
| 정책 목록 | 정책을 필터링하고 즐겨찾기하는 탐색 화면 |
| 정책 상세 | 지원 내용, 신청 기간, 조건, 서류, 일정 연결을 확인하는 화면 |
| 일정 생성 | 지역, 날짜, 제목을 단계별로 정해 새 여행을 만드는 화면 |
| 일정 목록 | 만든 여행을 카드로 확인하고 상세로 진입하는 화면 |
| 일정 상세 | 연결된 정책, 추천 정책, Day별 장소 타임라인을 보는 화면 |
| 마이페이지 | 프로필, 내 일정/즐겨찾기/신청 정책 수, 관심 정책 목록을 보는 화면 |

프로토타입의 핵심 경험은 "정책을 따로 검색하는 앱"이 아니라 "여행 일정을 만들고 그 일정에 맞는 혜택을 붙이는 앱"에 가깝다.

## End-To-End User Journey

1. 사용자는 이메일/비밀번호 또는 소셜 로그인 CTA로 앱에 진입한다.
2. 홈에서 이번 달 인기 정책, 인기 여행지, AI 추천 일정을 본다.
3. 사용자는 대표 정책 카드나 검색 영역을 눌러 정책 목록 또는 정책 상세로 이동한다.
4. 정책 목록에서는 할인, 지원금, 적립 같은 필터로 관심 정책을 좁힌다.
5. 마음에 드는 정책은 즐겨찾기에 저장하거나 상세 화면으로 들어간다.
6. 정책 상세에서 지원 금액, 신청 기간, 신청 대상, 필요 서류를 확인한다.
7. 사용자는 해당 정책을 기존 일정에 담거나, 정책이 연결된 새 일정을 만든다.
8. 새 일정 생성 시 지역, 날짜, 제목을 차례로 정하고 요약을 확인한다.
9. 일정 상세에서는 연결된 정책과 해당 일정에 어울리는 다른 정책 후보를 함께 본다.
10. 사용자는 Day 탭과 장소 타임라인을 보면서 여행 실행 계획을 확인한다.
11. 마이페이지에서는 내 일정 수, 즐겨찾기 정책 수, 신청 정책 수와 관심 정책 목록을 확인한다.

이 흐름에서 가장 중요한 전환은 `정책 상세 -> 일정 연결`이다. 프로토타입은 혜택 탐색을 일정 작성과 분리하지 않고, 정책을 여행 준비 과정 안으로 끌어온다.

## Login Flow

로그인 화면은 앱의 첫 신뢰 형성 지점이다.

사용자 경험 흐름:

1. 사용자는 앱 로고와 "숨은 여행 혜택을 사냥하세요" 메시지를 본다.
2. 이메일과 비밀번호 입력 필드가 기본으로 보인다.
3. 입력이 비어 있으면 오류 메시지가 표시된다.
4. 로그인 버튼을 누르면 로딩 상태가 표시되고 홈으로 이동한다.
5. 비밀번호 찾기와 회원가입 텍스트가 보이지만, 프로토타입에서는 실제 화면 전환이 없다.
6. Kakao/Google 버튼은 별도 provider 흐름이 아니라 같은 로그인 성공 흐름으로 연결된 mock CTA다.

해석:

- 프로토타입은 가입/인증보다 "로그인 후 정책-일정 경험"을 빠르게 보여주는 데 집중한다.
- 현재 실제 앱에서는 회원가입, 닉네임 설정, password reset, OAuth가 이미 별도 구현되어 있으므로 mock 동작은 가져오지 않는다. 대신 `/`와 `/login`의 첫 화면 시각 구조는 프로토타입 `LoginScreen` 기준으로 반영했다.

## Home Flow

홈은 정책 탐색과 일정 생성으로 이어지는 허브다.

사용자 경험 흐름:

1. 상단 검색형 영역을 누르면 정책 목록으로 이동한다.
2. 프로필 원형 버튼을 누르면 마이페이지로 이동한다.
3. 인사말 아래 대표 정책 카드가 크게 보인다.
4. 대표 정책 카드는 `지역사랑 휴가지원` 성격의 환급 혜택으로 상세 화면 진입을 유도한다.
5. `이번 달 혜택` 가로 카드 목록에서 여러 정책을 빠르게 훑는다.
6. `인기 국내 여행지` 가로 카드 목록에서 제주, 부산, 강원, 경주 같은 여행지를 선택하면 일정 생성으로 이동한다.
7. `AI 추천 맞춤 일정` 카드는 기존 일정 상세 또는 새 일정 생성으로 이어진다.
8. 하단 탭으로 홈, 정책, 일정, 마이페이지를 전환한다.

UX 의미:

- 홈은 "검색"보다 "발견"에 가깝다.
- 사용자는 정책명을 몰라도 대표 혜택, 인기 여행지, AI 추천 일정 중 하나를 눌러 시작할 수 있다.
- 정책 카드와 여행지 카드가 모두 일정 생성/상세로 이어지기 때문에, 앱의 중심 객체는 `여행 일정`이다.

현재 앱 반영 후보:

- 홈의 대표 정책 카드는 `지역사랑 휴가지원` 같은 시즌 핵심 정책을 강조하는 데 적합하다.
- 여행지 카드 클릭 시 바로 일정 생성으로 이어지는 흐름은 지역 기반 정책 추천과 잘 맞는다.
- AI 추천 일정 카드는 실제 AI 엔진이 붙기 전에도 "혜택 묶음 일정" 추천으로 활용할 수 있다.

## Policy Discovery Flow

정책 목록은 사용자가 관심 정책을 비교하고 저장하는 화면이다.

사용자 경험 흐름:

1. 사용자는 하단 탭 또는 홈 검색 영역에서 정책 목록으로 진입한다.
2. 상단에서 `정책` 화면 제목과 즐겨찾기 수를 본다.
3. 카테고리 필터로 전체, 할인, 지원금, 적립을 전환한다.
4. 정책 카드는 혜택 유형, D-day, 정책명, 지역, 마감일, 설명, 관심 수를 보여준다.
5. 카드를 누르면 정책 상세로 이동한다.
6. 하트 버튼을 누르면 즐겨찾기에 추가되거나 제거되고 toast가 표시된다.

UX 의미:

- 정책을 행정 문서처럼 보여주지 않고, 쇼핑/콘텐츠 카드처럼 빠르게 훑게 만든다.
- 필터는 복잡한 자격 판정보다 "혜택 성격"으로 먼저 나눈다.
- 즐겨찾기는 사용자가 아직 신청하지 않아도 관심 정책을 보관하는 가벼운 행동이다.

현재 앱 반영 후보:

- 실제 앱의 정책 목록에는 이미 discovery block이 있으므로, 이 프로토타입의 카드 구조는 유지하되 실제 정책 상태와 source confidence를 붙이는 쪽이 적절하다.
- `할인/지원금/적립` 분류는 `메인 지원금/교통 할인/지역 할인/적립` 같은 Travel Hunter 전용 taxonomy로 확장할 수 있다.

## Policy Detail Flow

정책 상세는 사용자가 "내가 이걸 신청할 가치가 있는지" 판단하는 화면이다.

사용자 경험 흐름:

1. 사용자는 정책 목록, 홈 대표 카드, 일정 상세 추천 정책에서 정책 상세로 진입한다.
2. 상단 hero에서 정책 태그, 마감 D-day, 정책명, 주관 기관을 확인한다.
3. 즐겨찾기 버튼으로 관심 정책에 저장한다.
4. 지원 내용 섹션에서 금액과 상세 설명을 본다.
5. 신청 기간 섹션에서 기간과 마감 경고를 본다.
6. 신청 대상 섹션에서 조건 체크리스트를 확인한다.
7. 필요 서류 섹션에서 준비해야 할 서류를 확인한다.
8. 하단 고정 CTA에서 `내 일정에 담기` 또는 `신청하기`를 선택한다.
9. `내 일정에 담기`를 누르면 기존 일정 선택 sheet가 열린다.
10. 기존 일정이 있으면 일정 카드 중 하나를 선택해 정책을 연결한다.
11. 기존 일정이 없거나 새 일정이 필요하면 `새 일정` 버튼으로 일정 생성 화면에 진입한다.
12. `신청하기`를 누르면 외부 사이트 이동 확인 모달이 열린다.

UX 의미:

- 정책 상세는 단순 소개 페이지가 아니라 "신청 전 판단"과 "일정에 연결"을 동시에 담당한다.
- 사용자는 정책을 저장하거나 신청하기 전에 일정과 먼저 묶어볼 수 있다.
- 필요 서류와 조건을 상세 화면 안에서 보여주기 때문에, 신청 과정의 불확실성을 줄인다.

현재 앱 반영 후보:

- `지역사랑 휴가지원` 상세 화면에서는 "대표 지원", "함께 확인할 교통 혜택", "지역 할인 후보", "신청 순서"를 같은 화면에 배치하는 방식이 적합하다.
- 외부 신청 버튼은 "Travel Hunter가 신청을 대신하지 않음"을 명확히 안내해야 한다.
- 일정 선택 sheet는 정책을 현재 여행 맥락에 붙이는 핵심 UX이므로 유지 가치가 높다.

## Schedule Creation Flow

일정 생성은 3단계 wizard로 구성되어 있다.

사용자 경험 흐름:

1. 사용자는 홈 여행지 카드, 일정 탭의 새 일정 FAB, 정책 상세의 새 일정 CTA에서 진입한다.
2. 정책 상세에서 들어온 경우, 상단에 연결 예정 정책이 먼저 표시된다.
3. 1단계에서 여행 지역을 선택한다.
4. 지역 선택 후 "다음" 버튼이 활성화된다.
5. 2단계에서 출발일과 도착일을 선택한다.
6. 날짜 선택 후 총 여행 일수가 계산된다.
7. 3단계에서 일정 제목을 입력한다.
8. 요약 박스에서 지역, 일정 기간, 인원, 연결 정책을 확인한다.
9. `일정 만들기`를 누르면 일정이 생성되고 일정 상세로 이동한다.

UX 의미:

- 사용자는 처음부터 긴 양식을 작성하지 않는다.
- 지역, 날짜, 제목을 순서대로 정하게 해 인지 부담을 낮춘다.
- 정책 상세에서 시작한 경우에도 일정 생성 과정에서 연결 정책 맥락이 유지된다.

현재 앱 반영 후보:

- 실제 앱은 이미 `/trips/new` 흐름이 있으므로, "정책 상세에서 진입한 일정 생성은 연결 정책을 계속 보여준다"는 경험을 강화할 수 있다.
- 지역 선택 단계에서 지역사랑 휴가지원 대상 지역 여부를 함께 표시하면 정책-일정 연결성이 더 강해진다.

## Schedule List Flow

일정 목록은 사용자가 만든 여행을 관리하는 화면이다.

사용자 경험 흐름:

1. 사용자는 하단 일정 탭에서 일정 목록으로 진입한다.
2. 상단에서 전체 일정 수를 확인한다.
3. 일정이 없으면 빈 상태 안내를 본다.
4. 일정이 있으면 카드 목록으로 여행을 본다.
5. 각 카드에는 D-day, 제목, 날짜, 여행 일수, 멤버, 연결 정책 수가 표시된다.
6. 카드를 누르면 일정 상세로 이동한다.
7. Floating action button으로 새 일정을 만들 수 있다.

UX 의미:

- 일정 목록은 단순 목록이 아니라 "내 여행 준비 현황"을 보여준다.
- 연결 정책 수를 카드에 표시해, 정책과 일정이 분리되지 않게 만든다.

현재 앱 반영 후보:

- 실제 `/trips` 카드에서도 연결된 혜택/정책 수와 확정 상태를 함께 보여주는 구조가 적합하다.
- 지역사랑 휴가지원 같은 대표 정책이 연결된 일정은 카드에서 더 분명히 드러나야 한다.

## Schedule Detail Flow

일정 상세는 여행 실행과 혜택 확인이 만나는 화면이다.

사용자 경험 흐름:

1. 사용자는 일정 목록, 홈 AI 추천 일정, 정책 연결 성공 후 일정 상세로 진입한다.
2. 상단 hero에서 일정 제목, D-day, 날짜, 지역 이미지를 확인한다.
3. 멤버 영역에서 동행자를 보고 친구 초대 CTA를 본다.
4. 연결된 정책이 있으면 먼저 표시된다.
5. 연결된 정책 카드를 누르면 정책 상세로 이동한다.
6. 아직 연결되지 않았지만 일정 지역과 맞는 추천 정책이 있으면 별도 영역에 표시된다.
7. Day 탭으로 여행 일차를 전환한다.
8. 선택한 Day의 장소 타임라인을 시간순으로 확인한다.
9. Day에 장소가 없으면 장소 추가 안내와 CTA가 보인다.
10. 장소 추가 CTA는 프로토타입에서는 준비 중 toast만 보여준다.

UX 의미:

- 일정 상세는 "어디 갈지"만 보는 화면이 아니라 "이 일정에서 어떤 혜택을 챙길 수 있는지"도 같이 보는 화면이다.
- 연결된 정책과 추천 정책을 모두 보여주기 때문에, 일정이 만들어진 뒤에도 혜택 탐색이 계속된다.
- Day별 장소 타임라인은 추후 교통 할인, 지역 할인, 방문 인증 체크리스트와 연결될 수 있다.

현재 앱 반영 후보:

- 일정 상세에 `이 여행에서 챙길 수 있는 혜택` 영역을 두고, 대표 지원/교통/지역 할인 후보를 묶어 보여주는 것이 자연스럽다.
- 장소 타임라인 근처에 지역 할인 후보를 붙이면 "이 장소에 가면 쓸 수 있는 혜택" 경험으로 확장할 수 있다.

## My Page Flow

마이페이지는 사용자의 활동 요약과 관심 정책 회수 동선이다.

사용자 경험 흐름:

1. 사용자는 홈 프로필 버튼 또는 하단 마이 탭에서 진입한다.
2. 상단에서 프로필 이름, 이메일, 편집 버튼을 본다.
3. 요약 카드에서 내 일정 수, 즐겨찾기 수, 신청 정책 수를 확인한다.
4. 즐겨찾기 정책 목록을 확인한다.
5. 관심 정책을 누르면 정책 상세로 이동한다.
6. 하트 버튼으로 즐겨찾기에서 제거할 수 있다.
7. 설정 메뉴에서 알림 설정, 공지/FAQ, 이용약관, 로그아웃을 볼 수 있다.
8. 로그아웃 외 메뉴는 준비 중 toast를 보여준다.

UX 의미:

- 마이페이지는 계정 설정보다 "내가 저장한 정책과 여행 준비 상태"를 회수하는 역할이 크다.
- 신청 정책 수가 별도 통계로 존재하므로, 향후 신청 상태 관리 UX와 연결 가능성이 높다.

현재 앱 반영 후보:

- 실제 앱의 마이페이지 일정 요약, 프로필 편집, 알림 설정, 연락처 저장 기능과 결합하면 좋은 구조다.
- 지역사랑 휴가지원처럼 신청 진행 단계가 긴 정책은 마이페이지에 `신청 준비 중`, `신청 완료`, `정산 필요` 같은 상태 요약으로 보여줄 수 있다.

## UX Strengths

- 모바일 앱형 화면 구성으로 주요 CTA가 엄지 접근 영역에 있다.
- 홈에서 정책, 여행지, 일정 추천을 한 번에 제시해 시작 경로가 다양하다.
- 정책 상세에서 조건, 서류, 신청 기간을 한 화면에서 보여줘 신청 전 판단이 쉽다.
- 정책을 일정에 담는 흐름이 명확하다.
- 일정 상세에서 연결된 정책과 추가 추천 정책을 함께 보여줘 여행 준비와 혜택 탐색이 이어진다.
- 일정 생성이 3단계로 나뉘어 있어 긴 양식보다 부담이 적다.
- 즐겨찾기와 toast feedback으로 사용자의 가벼운 저장 행동을 지원한다.

## UX Limitations

- 프로토타입 원본에서 로그인, Kakao/Google 시작, 회원가입, 비밀번호 찾기는 실제 인증 흐름이 아니라 mock 또는 미동작 CTA다. 현재 React 앱은 같은 화면 구조를 쓰되 실제 DB-backed login, signup, password reset, OAuth start route에 연결한다.
- 정책 데이터가 mock이며 실제 운영 상태, 종료 여부, 신청 차수, 공식 출처 신뢰도를 반영하지 않는다.
- 정책 자격 판정이 없다. 사용자가 실제로 신청 가능한지, 이미 참여했는지, 거주지 제한에 걸리는지는 알 수 없다.
- 외부 신청 모달은 실제 링크 이동보다 안내 모달 수준이다.
- 장소 추가는 준비 중 toast만 표시된다.
- 친구 초대, 알림 설정, FAQ, 이용약관 등 일부 메뉴는 준비 중 상태다.
- 일정 장소 타임라인은 고정 mock 데이터이며, 드래그 이동/수정/삭제 같은 실제 편집 UX는 없다.
- 신청 정책 수는 표시되지만 신청 상태 관리 흐름은 없다.

## Application Candidates For Current React App

현재 실제 앱에 반영할 만한 UX 후보는 다음 순서가 적절하다.

1. `지역사랑 휴가지원` 중심 혜택 패키지 화면
   - 대표 지원, 교통 혜택, 지역 할인 후보, 신청 순서를 한 화면에 묶는다.
   - "확정 신청 가능"이 아니라 "함께 확인할 혜택"과 "공식 확인 필요" 기준으로 안내한다.

2. 일정 상세의 혜택 연결 영역 강화
   - 연결된 정책만 보여주는 수준을 넘어, 해당 여행에서 챙길 수 있는 교통/지역 할인 후보를 같이 보여준다.
   - Day별 장소 타임라인과 지역 할인 후보를 연결할 수 있는 기반을 둔다.

3. 정책 상세 CTA 구조 정리
   - `내 일정에 담기`, `공식 신청 페이지 확인`, `필요 서류 확인`, `마감 알림`을 명확히 분리한다.
   - 신청 전/신청 후/정산 전 단계가 긴 정책에 맞는 상태 안내를 둔다.

4. 일정 생성 단계형 UX 보강
   - 지역 선택 단계에서 해당 지역의 대표 혜택 후보를 함께 보여준다.
   - 정책 상세에서 일정 생성으로 들어온 경우 연결 예정 정책을 계속 노출한다.

5. 마이페이지의 신청 상태 회수 동선
   - 즐겨찾기뿐 아니라 `신청 준비 중`, `신청 완료`, `정산 필요` 같은 상태별 정책을 다시 확인할 수 있게 한다.
